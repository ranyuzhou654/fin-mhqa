## 规则

### 1. 错误分类

每个报错会被归为三类之一。前两类属于基础设施问题，第三类是 Agent 本身的失败。

| 类别 | 例子 | 性质 |
| --- | --- | --- |
| `quota` | HTTP 402；HTTP 429 且响应内容指明是用量或计费限制（如 `GoUsageLimitError`） | 基础设施 |
| `transport` | 连接断开、IncompleteRead、超时、HTTP 5xx、重试后仍失败的普通 429 限流 | 基础设施 |
| `agent` | 输出格式修复后仍不合法、规划结构错误、发布守卫拒绝等 | Agent 失败，是一次有效结果 |

分类依据是 `result.json` 中记录的报错文本，规则有测试覆盖，测试用例取自历史运行中的真实报错。

### 2. 额度用完就立即停

- **模型客户端**：遇到额度类错误时抛出 `QuotaExhausted`，不重试。普通 429 限流仍按原来的规则重试。
- **运行器**：出现额度错误后，不再启动新题；已经在运行的题照常结束。之后写入 `run_status.json`（状态为 `INCOMPLETE`，并记录 `stopped_by_quota`），退出码为 3。
- **驱动脚本**：收到退出码 3 时，整个驱动立即停止，不再启动后续运行。

### 3. 逐题续跑

`run_agent_dev.py --resume` 用于继续一个未完成的运行：

- **只补跑三种题**：还没开始的、开始了但没有结果的、以基础设施报错结束的。
- **Agent 失败不重跑**：以 Agent 失败结束的题是有效结果，保持不动。
- **旧结果不删除**：被补跑的题原来的目录移到 `superseded/<arm>/<id>__<n>`。这个位置在 arm 目录之外，审计和评分不会读到它，但证据仍然保留。
- **先校验再续跑**：续跑前会比对原运行的问题文件、配置、代码 sha256、模型、故障计划和索引健康状态，任何一项不同都拒绝续跑，要求换一个新的运行目录。这样一次运行内部不会混入不同版本的代码或配置。
- **状态记录**：每次运行或续跑结束，都会在 `run_status.json` 中追加一条历史记录。

驱动脚本（`lib_run.zsh`）的处理规则：

- 已完成的运行直接跳过，包括状态为 `COMPLETE` 的运行，以及在本机制之前完成、有 `health_after.json` 的旧运行；
- 未完成的运行会自动加上 `--resume` 继续。

### 4. 评分

- **默认不评分未完成的运行**：`evaluate_benchmark.py` 和 `fault_report.py` 拒绝为 `INCOMPLETE` 的运行评分。`evaluate_benchmark.py` 加 `--allow-incomplete` 后可以强制评分，未完成的题算错。
- **报错分类单列**：评分报告新增 `errors_by_class`，把基础设施报错和 Agent 报错分开统计。所有报错仍然计入分母，都算错。

## 与旧结果比较时的规定

- **不溯及既往**：本机制启用之前的运行，基础设施报错按当时的规则算错，而且没有补跑，这些结果保持不变。
- **新旧运行比较时同时报告两种口径**：新运行会补跑基础设施报错，所以和旧运行比较时会略占便宜：
  - 按记录的原始结果比较；
  - 排除任一方有基础设施报错的题后，再做配对比较。

  例如 [故障注入第 1 轮](../experiments/FAULT_INJECTION_V1_RESULTS.md) 中，B2 有 5 题因传输中断报错，就属于这种情况。
