# 运行 harness

2026-09-26 起生效，对应路线图 P1.1–P1.2。代码在 `src/finmhqa/harness/runs.py`、`scripts/run_agent_dev.py` 和 `scripts/lib_run.zsh`，测试在 `tests/test_harness.py`。

## 为什么需要

这几天的运行里发生过三类事故：

| 日期 | 事故 | 损失 |
| --- | --- | --- |
| 09-26 | OpenCode Go 每周额度在约 01:00 用完，驱动脚本继续逐题请求，每题都失败 | 150 题的无故障 Dev 全部作废 |
| 09-24、09-25 | 用户中途暂停 | 两次运行只能整体归档，之后从头重跑 |
| 09-25 | 响应传到一半时连接断开（IncompleteRead），没有被重试 | 2 题直接算错 |

## 规则

### 1. 错误分类

每个报错会被归为三类之一。前两类属于基础设施问题，第三类是 Agent 本身的失败。

| 类别 | 例子 | 性质 |
| --- | --- | --- |
| `quota` | HTTP 402；HTTP 429 且响应内容指明是用量或计费限制（如 `GoUsageLimitError`） | 基础设施 |
| `transport` | 连接断开、IncompleteRead、超时、HTTP 5xx、重试后仍失败的普通 429 限流 | 基础设施 |
| `agent` | 输出格式修复后仍不合法、规划结构错误、发布守卫拒绝等 | Agent 失败，是一次有效结果 |

分类依据是 `result.json` 中记录的报错文本，规则有测试覆盖，测试用例取自历史运行中的真实报错。

### 2. 额度用完就立即停

- **模型客户端**：遇到额度类错误时抛出 `QuotaExhausted`，不重试。普通 429 限流仍按原来的规则重试。
- **运行器**：出现额度错误后，不再启动新题；已经在运行的题照常结束。之后写入 `run_status.json`（状态为 `INCOMPLETE`，并记录 `stopped_by_quota`），退出码为 3。
- **驱动脚本**：收到退出码 3 时，整个驱动立即停止，不再启动后续运行。

### 3. 逐题续跑

`run_agent_dev.py --resume` 用于继续一个未完成的运行：

- **只补跑三种题**：还没开始的、开始了但没有结果的、以基础设施报错结束的。
- **Agent 失败不重跑**：以 Agent 失败结束的题是有效结果，保持不动。
- **旧结果不删除**：被补跑的题原来的目录移到 `superseded/<arm>/<id>__<n>`。这个位置在 arm 目录之外，审计和评分不会读到它，但证据仍然保留。
- **先校验再续跑**：续跑前会比对原运行的问题文件、配置、代码 sha256、模型、故障计划和索引健康状态，任何一项不同都拒绝续跑，要求换一个新的运行目录。这样一次运行内部不会混入不同版本的代码或配置。
- **状态记录**：每次运行或续跑结束，都会在 `run_status.json` 中追加一条历史记录。

驱动脚本（`lib_run.zsh`）的处理规则：

- 已完成的运行直接跳过，包括状态为 `COMPLETE` 的运行，以及在本机制之前完成、有 `health_after.json` 的旧运行；
- 未完成的运行会自动加上 `--resume` 继续。

### 4. 评分

- **默认不评分未完成的运行**：`evaluate_benchmark.py` 和 `fault_report.py` 拒绝为 `INCOMPLETE` 的运行评分。`evaluate_benchmark.py` 加 `--allow-incomplete` 后可以强制评分，未完成的题算错。
- **报错分类单列**：评分报告新增 `errors_by_class`，把基础设施报错和 Agent 报错分开统计。所有报错仍然计入分母，都算错。

## 与旧结果比较时的规定

- **不溯及既往**：本机制启用之前的运行，基础设施报错按当时的规则算错，而且没有补跑，这些结果保持不变。
- **新旧运行比较时同时报告两种口径**：新运行会补跑基础设施报错，所以和旧运行比较时会略占便宜：
  - 按记录的原始结果比较；
  - 排除任一方有基础设施报错的题后，再做配对比较。

  例如 [故障注入第 1 轮](../experiments/FAULT_INJECTION_V1_RESULTS.md) 中，B2 有 5 题因传输中断报错，就属于这种情况。

## 录制—重放回归测试（P1.3）

代码在 `src/finmhqa/harness/replay.py`，命令为 `scripts/replay_check.py --runs <运行目录…>`，测试在 `tests/test_replay.py`。这项检查不调用模型，也不需要检索服务。

重放时，用当前代码的 `AgentGraph` 重新执行一条已录制的轨迹：

- **模型调用**：返回录制下来的决策。但返回之前，先检查当前代码构造的模型输入（提示词加历史）和输出 schema，是否与录制时的 `step_NN/input.txt`、`schema.json` 逐字节一致。不一致就说明录制的回复已经不适用，判定为分歧，并报告分歧出现在第几步。
- **检索和上下文读取**：按完全相同的参数，查找录制下来的返回。如果 Agent 现在发出了录制时没有的参数，同样判定为分歧。
- **计算器**：真实执行。
- **事件流**：重放产生的完整事件流必须与录制的逐条一致，耗时字段除外。

**历史验证**：2026-09-26 对 27 次历史运行（B2/B3 各版本的 Dev 运行和故障运行）共 1,278 道题做了重放，**全部一致，每一步的模型输入都逐字节相同**。见 [报告](../evidence/harness/replay_history_2026-09-26.json)。这说明后续新增的核验 v2、规划者 v2、harness 改动都没有改变 v1 配置的行为，之前所说的「v1 保持冻结」有了直接证据。

**能发现回归**：测试中故意做了三种改动，都被检出：

- 把重规划预算改为 0，事件流分歧；
- 在核验提示词末尾加一句话，在第一次核验调用处报告输入不同，之前的规划步骤不受影响；
- 篡改录制的检索参数，报告出现了录制中没有的检索调用。

**局限**：重放只能验证「输入不变时，行为不变」。只要改动了提示词或模型能看到的内容，就必须重新真实运行，重放会明确报告这种情况，而不会给出错误的「一致」。

## 来源记录与金丝雀（P1.4）

- **清单新增字段**：每次运行的清单新增 `git` 字段，记录 commit、工作区是否有未提交改动，以及改动的文件列表。模型的原始响应中本来就保存了提供方返回的模型名。
- **模型名无法反映接口差异**：提供方只返回 `deepseek-v4.1-flash`，没有版本指纹。Zen 和 Go 两个接口返回的模型名相同，所以之前那次接口差异，只看这个字段是发现不了的。
- **金丝雀**：`scripts/canary.py` 用 [canary_v1](../../configs/canary_v1.json) 中固定的 5 道 Dev 题（T1–T5 各 1 道），用给定配置跑一遍。
  - **选题标准**：这 5 道题在三个最近配置的全部 9 次 Dev 运行中都答对（45/45）。
  - **判定规则**：至少答对 4 道，且没有基础设施报错，才算通过；遇到额度错误时退出码为 3。
  - **驱动脚本**：开跑前默认先过金丝雀这一关；设置 `CANARY=0` 可以跳过。
  - **运行状态**：首次真实运行要等额度恢复；测试里已经用模拟的「漂移提供方」验证过判定逻辑。

## 运行登记表与成本预检（P1.5）

- **运行登记表**：`scripts/run_registry.py` 扫描全部运行，生成 `data/bench/runs/REGISTRY.{json,md}`。表中列出类别（有效 / 作废 / 中止 / 被取代）、状态、准确率、错误分类、平均模型调用次数、每题 token 数和 git commit。
  - Test 运行默认不列准确率，避免登记表变成偷看 Test 结果的途径。
  - 当前快照见 [run_registry_2026-09-26.md](../evidence/harness/run_registry_2026-09-26.md)。
- **成本预检**：`scripts/cost_estimate.py` 按同一配置的历史运行估算一批运行的 token 消耗。设置 `TOKEN_LIMIT` 后，驱动脚本会在超出上限时拒绝开跑。
  - 提供方的 API 查不到剩余额度，所以上限要由用户根据控制台上的剩余额度自己填写。
  - 估算偏保守：规划者 v2 目前只有故障运行的记录，而故障运行每题约 14 万 token，高于无故障运行。

## 检索资源锁（P1.6）

`retrieval_lock()` 用文件锁 `data/.retrieval.lock`，在多个进程之间串行访问只有一个推理槽的检索服务。运行器和实时演示都会先拿锁再检索。测试用 3 个进程同时争用，确认持有时间段互不重叠。

## CI（P1.7）

`.github/workflows/tests.yml` 在每次 push 和 PR 时运行：

- 用本地开发同样的两个锁文件安装依赖；
- 跑全部测试；
- 重放示例轨迹。

在本地模拟过这个流程：从全新克隆的仓库、只按锁文件安装依赖，结果为 219 项通过、3 项跳过。跳过的 3 项都依赖不纳入 git 的本地数据。GitHub 上的首次运行要等推送之后才能确认。
