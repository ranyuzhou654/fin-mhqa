## 三、项目经历

**财报多跳问答 Agent** ｜ 个人项目 ｜ 2026.09 – 2026.10

技术栈：Python、LangGraph、Docling、bge-m3、bge-reranker-v2-m3、FAISS、BM25（jieba）、FastAPI、SSE、SQLite、DeepSeek API

**完整版（5 条）**

> **背景**：财报问答需要跨公司、跨报表的多跳推理与精确计算，口径、期间或单位一错即答错。单次检索的 Naive RAG 无法根据中间结果规划下一步检索，实测条件桥接类问题准确率仅 13%；多角色 Agent 的收益也缺少可靠的 Benchmark 来验证。

- **解析与检索**：基于 Docling（Layout + TableFormer）解析 10 家上市公司半年报共 1,750 页，按正文 / 表格 Markdown / 表格 Key-Value 三类 Chunking，得到 9,322 个可溯源 chunk。检索采用 Dense（bge-m3）+ BM25 双路召回，经 RRF 融合后用 Cross-Encoder Rerank，Hit@5 达 96.7%，MRR@10 达 0.81。分阶段 Ablation 显示，Rerank 使多跳题全跳覆盖率从 70% 提升至 84%。
- **Agent 编排**：基于 LangGraph 实现 Planner / Executor / Verifier 多角色 Agent，Tool Calling 覆盖检索、上下文读取和 Decimal 计算器，并设置分层调用预算，为 Verifier 预留调用。输出侧的约束有两条：答案数值必须来自计算器，引用必须是已检索到的原文。引入 JSON Schema 校验 + Self-Repair 后，单 Agent 准确率由 92.7% 提升至 98.7%（+6.0pp）。
- **Benchmark 构建**：用会计勾稽关系与跨表一致性核验 298 条财务事实，按 6 类题型程序化生成 150 道多跳题及精确答案（Dev 50 / Test 100），答案不依赖人工标注。按事实组合划分以防数据泄漏，用双 LLM-as-Judge 做歧义审查；Test 只允许事先登记的配置运行。
- **Ablation 与 Fault Injection**：逐级 Ablation 显示，Retrieval 带来 +42.7pp，Agent Loop 再带来 +31.3pp，多角色在干净证据下无显著收益。设计盲 Fault Injection（单位错标、本期 / 上期列错位、冲突摘要表），发现原版 Verifier 无净收益；基于 Trajectory 分析加入来源优先级、期间列核对等 4 条规则后，列错位场景下准确率较单 Agent 高 20.5pp（Dev，95% CI [4.5, 36.4]）。
- **服务化**：基于 FastAPI + SSE 实现多用户 Agent 服务，事件先持久化再推送，支持 Last-Event-ID 断线续传、按用户 Fair Scheduling、Rate Limit 与 Token 配额。压测中事件零丢失，轻负载用户的 P50 排队时延由 47.5s 降至 10.6s。另配套 Record-Replay 回归测试，1,278 条历史轨迹回放一致。

**精简版（3 条，适合一页简历）**

- 构建财报多跳问答的 RAG + Agent 系统：用 Docling 解析 1,750 页半年报，得到 9,322 个 chunk；Dense + BM25 双路召回经 RRF 融合与 Cross-Encoder Rerank，Hit@5 为 96.7%；基于 LangGraph 实现 Planner / Executor / Verifier 多角色编排，数值由计算器 Tool 给出，并附原文引用。
- 自建 150 题程序化 Benchmark，答案由 298 条核验过的事实计算得出；逐级 Ablation 量化各组件收益：Retrieval +42.7pp、Agent Loop +31.3pp、JSON Schema Self-Repair +6.0pp。通过盲 Fault Injection 诊断并改进 Verifier，列错位场景下比单 Agent 高 20.5pp（Dev）。
- 基于 FastAPI + SSE 实现多用户服务，支持断线续传、Fair Scheduling 与 Rate Limit，压测事件零丢失；配套 Record-Replay 回归与事先登记的实验流程。

**个人边界（自己掌握，不写进简历）**：
- 「独立完成」指没有团队，方案、实验设计和取舍都由本人决定。大模型通过 API 调用，没有训练；解析、向量和重排模型都是开源模型。
- Hit@5 96.7%（30 题中 29 题）来自修正后的源页等价标签。修正前后检索结果完全相同，分数提升来自标签修正，不是算法改进。被问到时要能说清楚。
- 「+20.5pp」只是 Dev 结果，而且 Verifier 规则是在同一批 Dev 故障上设计的，所以简历上必须注明「Dev」。
- 原设计有四个角色。第四个 Synthesizer 在最终配置里只把核验通过的答案原样发布，不调用模型，所以简历写 Planner / Executor / Verifier 三个角色。
- 「Tool Calling」指模型输出 JSON 动作，由执行器调用工具，不是厂商原生的 function calling 接口。被问到时要说明。
- 「全跳覆盖率」指多跳题的每一跳证据都进入前 5 名的比例；用的是每跳一条标准查询，不是 Agent 实际发出的查询。

**项目背景（面试展开版）**

**为什么做**：分析师常问这样的问题：「比较比亚迪与宁德时代的营收，选较高的一家，再算它的研发费用率」。回答它要先比较，再根据结果查第二个指标；还要分清合并 / 母公司、本期 / 上期、元 / 千元；最后精确计算并给出出处。

**现有做法的不足**（都是本项目实测到的）：
1. **传统 RAG 不会多步决策**：检索一次、回答一次的做法整体准确率 61%，「先比较再查询」类题只有 13%，三步以上的题只有 22%。
2. **表格解析不可靠**：关键数据几乎都在表格里，普通解析工具会拆碎多行表头、漏掉整张利润表，单位还常常只写在报告开头。
3. **只看准确率会高估能力**：不检索也能答对 19%，说明模型可能见过这些公开财报，所以必须同时检查每个数字有没有真实出处。
4. **多角色的价值说不清**：证据正确时，多角色 Agent 和单模型 Agent 准确率几乎一样，成本却更高；原来的 20 题开发集两者都是满分，根本区分不出来。

**所以项目的目标**：
- 先建一个答案可自动复算、测试集严格隔离的评测集；
- 逐项量化每种技术的收益；
- 用人为制造的错误证据，回答「核验角色什么时候有用」；
- 最后做成可演示的多用户服务。

> 您好，我主要做大模型应用和 Agent 方向。代表项目是一个上市公司财报问答 Agent。起因是传统 RAG 只检索一次，遇到「先比较、再查询」的问题准确率只有 13%。

> 我做了混合检索，检索命中率 96.7%，又用 LangGraph 实现了规划、执行、核验多角色 Agent。我最看重的是评估：自建了 150 道题的评测集，答案由核验过的财务事实自动算出。结果发现，检索和多步推理是主要收益来源，而多角色只在证据出错时才有价值；改进核验规则后，这类情况下准确率比单模型高 20 个百分点。系统还做成了多用户服务。希望有机会详细交流。

**一分钟面试自我介绍（项目部分）**

> 我做的是上市公司财报问答 Agent。难点在于问题常常要多步推理，口径、期间、单位一错就答错。
>
> 我发现两个问题：一是 Naive RAG 只检索一次，条件桥接类问题准确率只有 13%；二是多角色 Agent 到底有没有用，原来的 20 题 Dev 集已经饱和，单 Agent 和多角色都是满分，区分不出来。
>
> 所以我先建了 Benchmark，答案由程序从核验过的财务事实计算得出。逐级 Ablation 发现，Retrieval 带来 42.7pp，Agent Loop 再带来 31.3pp，但多角色在干净证据下没有显著收益。为了弄清 Verifier 的价值，我做了盲 Fault Injection，发现原版 Verifier 也拦不住错误；分析 Trajectory 后补了 4 条规则，在列错位场景下比单 Agent 高 20.5pp。
>
> 整个过程我坚持先登记判定标准再跑实验。比如上下文压缩省了 37%–44% 的输入 token，但没达到事先定的 40% 门槛，我就没有采用，而是用只替换 Verifier 输入视图的 Replay 实验定位到了真正的原因。
