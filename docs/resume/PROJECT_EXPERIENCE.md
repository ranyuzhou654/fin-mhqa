## 三、项目经历

**财报多跳问答 Agent** ｜ 个人项目 ｜ 2026.09 – 2026.10

技术栈：Python、LangGraph、Docling、bge-m3 / bge-reranker-v2-m3、FAISS、BM25、FastAPI、SSE、SQLite、DeepSeek API

**项目背景（简历版，放在要点之前）**

> 财报问答常常要跨公司、跨报表做多步计算，合并 / 母公司口径、本期 / 上期、元 / 千元稍有偏差就会答错。现有方案在这里有三个不足：
> - 固定 RAG 只检索一次，无法根据中间结果决定下一步，实测条件桥接题准确率仅 13%；
> - 通用 PDF 解析会拆碎复杂表头、漏检整张报表；
> - 多角色 Agent 缺少可靠评测，说不清是否有效、何时有效。
>
> 本项目在 10 家上市公司半年报上构建可评测、可追溯的多跳问答 Agent，并量化每项技术的真实收益。

**完整版（6 条，适合项目篇幅充足的简历）**

- **数据与切片**：用 Docling 版面与表格结构模型解析 10 家上市公司半年报，共 1,750 页。设计正文、表格 Markdown、表格键值三类切片，每块带可追溯元数据，构建 9,322 条证据块。替换解析器前先用难例小样做对照，16 个源页事实锚点全部通过。
- **混合检索**：搭建「向量 + BM25 双路召回 → RRF 融合 → 交叉编码器重排」流水线，开发集 Hit@5 为 96.7%，MRR@10 为 0.81。一次检索拆成 6 种方案做分阶段消融：融合比单路 BM25 的 Hit@5 高 33pp；重排使多跳题「每一跳都命中」从 70% 提升到 84%。还定位到等价副本在 RRF 截断时一起被丢掉的「分票」问题。
- **Agent 编排**：基于 LangGraph 设计规划、执行、核验、综合四角色 Agent，配备受控上下文读取工具和 Decimal 计算器，设置分层预算并为核验预留调用，发布门禁要求数值必须来自计算器、引用必须是已观测证据。引入 JSON Schema 校验与带错误反馈的格式修复后，单模型 Agent 准确率从 92.7% 提升到 98.7%（+6.0pp，95% CI [2.7, 10.0]），格式报错清零。
- **评测体系**：不依赖人工标注答案，以会计恒等式和跨表一致性核验 298 条事实，按 6 类题型程序化生成 150 道多跳题及精确答案（Dev 50 / Test 100）。配套防泄漏划分、双模型歧义审查，以及 Test 访问保护（只有登记过的配置能跑，运行记录只追加）。
- **消融与故障注入**：逐级消融显示，检索带来 +42.7pp，Agent 循环再带来 +31.3pp（桥接题从 13% 提升到 92%），并如实给出「干净证据下多角色没有显著收益」的结论。随后设计不带任何提示的盲故障注入，发现原版核验角色没有净收益；按轨迹诊断提出 4 条核验规则后，四角色 Agent 在列错位故障下比单模型高 20.5pp（95% CI [4.5, 36.4]），纠正题数从 6 题增加到 15 题，误伤从 7 题降到 2 题（Dev 结果）。
- **工程化**：把 Agent 封装为 FastAPI + SSE 多用户服务。事件先持久化再推送，支持断线续传；按用户公平调度，并有限流与配额。压测中事件零丢失，轻度用户的排队中位数从 47.5s 降到 10.6s。另外搭建了录制—回放回归（1,278 道历史题回放一致）和额度中断自动续跑的实验 harness。

**精简版（3 条，适合一页简历）**

> 项目背景：固定 RAG 无法完成需要按中间结果决策的多跳财报问答（实测桥接题 13%），多角色 Agent 也缺少可靠评测。本项目构建可评测、可追溯的多跳问答 Agent，并量化每项技术的收益。

- 构建财报多跳问答的 RAG + Agent 系统：Docling 解析 1,750 页半年报，生成 9,322 条证据块；向量与 BM25 双路召回，经 RRF 融合和重排，开发集 Hit@5 为 96.7%；基于 LangGraph 实现规划、执行、核验、综合四角色 Agent，配合计算器与发布门禁。
- 自建程序化评测集（298 条核验事实，150 道多跳题），用配对置信区间完成逐级消融：检索 +42.7pp，Agent 循环 +31.3pp，格式修复 +6.0pp。通过盲故障注入诊断并改进核验角色后，列错位故障下准确率比单模型高 20.5pp（Dev）。
- 封装为 FastAPI + SSE 多用户服务（断线续传、公平调度、限流配额，压测事件零丢失），并搭建录制—回放回归与事先登记的实验流程，保证结论可复现。

**项目背景（面试展开版）**

**为什么做**：上市公司财报是典型的高价值、强约束文档，分析师常问这样的问题：「比较比亚迪与宁德时代的营收，选较高的一家，再算它的研发费用率」。回答它需要：
- 找到两家公司的报表；
- 先比较，再根据比较结果去查第二个指标；
- 处理口径、期间、单位；
- 精确计算并给出出处。

一个数字错位就是错答，而且必须能说清依据。

**现有技术的不足**（都是本项目实测或观察到的）：

1. **固定 RAG 不会多步决策**：「检索一次、回答一次」的流水线在 Dev 上只有 61.3%，条件桥接题 13%，三跳题 22%。它无法根据第一步的结果决定第二步查什么。
2. **PDF 表格解析不可靠**：财报的关键信息几乎都在表格里。通用规则解析器会把多行表头拆碎、漏检整张利润表；续表没有标题，单位常常只写在报告开头。检索拿到的块如果表头错了，后面全错。
3. **只看最终准确率会被高估**：闭卷（不检索）就能答对 18.7%，有些答案精确到小数，说明模型可能见过这些公开财报。所以必须同时检查每个数字是否来自真实引用。
4. **多角色 Agent 的收益说不清**：在干净证据上，规划 + 核验的四角色 Agent 相对单模型只高 0.7pp（区间跨 0），却多花 23% 的调用、约 2 倍的输出 token。核验角色到底有没有用、什么时候有用，缺少能回答这个问题的评测。
5. **原有开发集无法区分架构**：项目早期用的 20 题开发集已经饱和，单模型 Agent 和多角色 Agent 都是 20/20，无法判断哪种更好。人工或模型撰写的答案在金额题上又难免有标注噪声，所以需要一个更难、答案可程序复算的评测集。

**因此本项目的目标**：
- 先建一个答案可程序复算、Test 有访问保护的评测集；
- 在同一个评测集上，逐项量化检索、Agent 循环、格式修复、多角色核验、上下文压缩等技术的收益；
- 用故障注入回答「核验角色在什么条件下有价值」；
- 最后把系统封装成可演示的多用户服务。

**写法说明（个人边界）**：
- 「独立完成」是指没有团队，方案、实验设计和取舍都由本人决定。底座大模型通过 API 调用，没有做训练；解析、向量和重排模型都是开源模型。
- 检索 29/30 的成绩来自修正后的源页等价标签。面试中要说明：修正标签前后排序结果完全相同，分数提升来自标签修正，不是算法改进。

**一分钟面试自我介绍（项目部分）**

> 我想用一个项目说明我怎么做 Agent。场景是上市公司财报问答，难点在口径、期间、单位和多跳推理。
>
> 我发现现有做法有两个问题：一是固定 RAG 只检索一次，遇到「先比较、再查另一家的指标」这类题，准确率只有 13%；二是多角色 Agent 到底有没有用，我手上的 20 题开发集已经饱和，单模型和多角色都是满分，根本区分不出来。
>
> 我先建了评测集：答案由程序从 298 条核验过的事实算出来，避免标注噪声。然后做逐级消融，发现检索带来 42 个百分点、Agent 循环再带来 31 个百分点，但多角色在干净数据上没有收益。为了弄清核验角色到底有没有用，我做了不给提示的故障注入，结果原版核验也没有净收益。我看了轨迹，发现它缺少「来源优先级」和「期间列核对」，补上四条规则后，它在列错位故障下比单模型高 20 个百分点。
>
> 整个过程中，我坚持先登记判定标准。比如上下文压缩省了约四成 token、准确率也没降，但没达到事先定的门槛，我就没有采纳，而是用重放实验找到了真正的原因：核验者在计数来源时偏宽松。
