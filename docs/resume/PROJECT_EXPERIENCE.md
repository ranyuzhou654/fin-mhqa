## 三、项目经历

**财报多跳问答 Agent** ｜ 个人项目 ｜ 2026.09 – 2026.10

技术栈：Python、LangGraph、Docling、bge-m3、BM25、FAISS、FastAPI、SQLite、DeepSeek API

**完整版（5 条）**

> **背景**：分析财报常要跨公司、跨报表多步计算，口径或单位一错就答错。传统 RAG 只检索一次，无法根据中间结果决定下一步，实测「先比较、再查询」类问题只有 13% 的准确率；多角色 Agent 是否有效也缺少可靠的评测来回答。

- **文档解析与检索**：用开源文档解析模型处理 10 家上市公司半年报（1,750 页），按正文和表格切分为 9,322 个文本块。检索采用「向量 + 关键词」双路召回、排名融合和重排模型，开发集前 5 条结果的命中率为 96.7%。
- **Agent 设计**：基于 LangGraph 实现规划、执行、核验三类角色，配备检索、读取上下文和精确计算三种工具。答案中的数字必须来自计算工具，引用必须是真实检索到的原文。加入输出格式校验与自动纠错后，单模型版本的准确率从 92.7% 提升到 98.7%。
- **评测集构建**：为避免人工标注误差，先用会计勾稽关系核验出 298 条财务事实，再按 6 类题型自动生成 150 道多跳题及精确答案。开发集与测试集严格隔离，只有事先登记的方案才能在测试集上运行。
- **效果分析与改进**：逐级对比显示，检索带来 43 个百分点的提升，多步 Agent 再带来 31 个百分点，而多角色在证据正确时没有额外收益。为检验核验角色的价值，人为制造错误证据（如本期与上期数据互换），发现原版核验无效；分析运行记录后补充 4 条核验规则，在这类错误下比单模型准确率高 20 个百分点（开发集）。
- **工程化**：把 Agent 封装为支持多用户的流式服务，可实时展示每一步推理和引用证据，支持断线续传、按用户公平排队和限流。压测中消息零丢失，轻度用户的排队时间从 47.5 秒降到 10.6 秒。

**精简版（3 条，适合一页简历）**

- 构建财报多跳问答的 RAG + Agent 系统：解析 10 家上市公司半年报，采用「向量 + 关键词」双路召回加重排模型，检索命中率 96.7%；基于 LangGraph 实现规划、执行、核验多角色 Agent，答案数字由计算工具给出，并附原文引用。
- 自建 150 道多跳题的评测集，答案由核验过的财务事实自动算出。据此逐项量化：检索 +43 个百分点，多步 Agent +31 个百分点，格式纠错使单模型版本 +6 个百分点。人为注入错误证据后改进核验规则，在这类错误下准确率比单模型高 20 个百分点。
- 封装为多用户流式服务，支持断线续传与公平排队，压测中消息零丢失。

**个人边界（自己掌握，不写进简历）**：
- 「独立完成」指没有团队，方案、实验设计和取舍都由本人决定。大模型通过 API 调用，没有训练；解析、向量和重排模型都是开源模型。
- 检索命中率 96.7%（30 题中 29 题）来自修正后的标签。修正前后检索结果完全相同，提升来自标签修正，不是算法改进。被问到时要能说清楚。
- 「高 20 个百分点」只是开发集结果，而且核验规则是在同一批开发集错误上设计的，所以简历上要写明「开发集」。
- 原设计有四个角色。第四个「综合」在最终配置里只是把核验通过的答案原样发布、不调用模型，所以简历写三类角色。

**项目背景（面试展开版）**

**为什么做**：分析师常问这样的问题：「比较比亚迪与宁德时代的营收，选较高的一家，再算它的研发费用率」。回答它要先比较，再根据结果查第二个指标；还要分清合并 / 母公司、本期 / 上期、元 / 千元；最后精确计算并给出出处。

**现有做法的不足**（都是本项目实测到的）：
1. **传统 RAG 不会多步决策**：检索一次、回答一次的做法整体准确率 61%，「先比较再查询」类题只有 13%，三步以上的题只有 22%。
2. **表格解析不可靠**：关键数据几乎都在表格里，普通解析工具会拆碎多行表头、漏掉整张利润表，单位还常常只写在报告开头。
3. **只看准确率会高估能力**：不检索也能答对 19%，说明模型可能见过这些公开财报，所以必须同时检查每个数字有没有真实出处。
4. **多角色的价值说不清**：证据正确时，多角色 Agent 和单模型 Agent 准确率几乎一样，成本却更高；原来的 20 题开发集两者都是满分，根本区分不出来。

**所以项目的目标**：
- 先建一个答案可自动复算、测试集严格隔离的评测集；
- 逐项量化每种技术的收益；
- 用人为制造的错误证据，回答「核验角色什么时候有用」；
- 最后做成可演示的多用户服务。
