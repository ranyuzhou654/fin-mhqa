# 核验角色 v2：结果

2026-09-25。按[事先登记的设计](VERIFIER_V2_PLAN.md)进行。

- **比较对象**：B3 + 修复 + 核验角色 v2（下称 B3v2），对比第 1 轮的 B3 + 修复（核验角色 v1）和 B2 + 修复（单模型）。
- **运行**：故障条件 F1、F2、F3 各 1 轮，每轮 44 题；无故障 Dev 3 次，每次 50 题。
- **审计**：282 条轨迹全部通过。
- **性质**：这是 Dev 结果，而且 v2 是看过这批 Dev 故障结果之后设计的，见文末的限制。

## 核验角色机制（第一次候选 → 最终发布）

| 故障 | 纠正 | 损害 | 漏过 | 拦截错误 / 误拦正确（决策次数） |
| --- | ---: | ---: | ---: | --- |
| F1 | 0（v1 1） | 0（v1 1） | 1（v1 1） | 0 / 12（v1 1 / 4） |
| F2 | **12（v1 5）** | 1 被误导 + 1 报错（v1 0） | **3（v1 12）** | **14 / 9（v1 5 / 3）** |
| F3 | 3（v1 0） | **0（v1 6）** | 2（v1 3） | 5 / 3（v1 1 / 29） |

- **F3**：v1 的「冲突无限拒绝」基本消失，误拦从 29 次降到 3 次，没有正确候选再被拖成拒答。反而有 3 个取自假摘要表的候选被纠正。
- **F2**：拦截从 5 次升到 14 次，纠正从 5 题升到 12 题，漏过从 12 题降到 3 题。「单一来源交叉核对」和「期间列核对」起了作用。
- **代价**：v2 在没有错误的地方也会要求交叉核对。F1 误拦 12 次，无故障 Dev 3 次运行共误拦 51 次（v1 为 10 次），其中 59 条理由是 NEEDS_CROSS_CHECK。这些题补查之后大多仍然正确发布，所以代价主要体现在成本上，对准确率影响不大。

## 事先登记的成功判定

| 条件 | 结果 | 判定 |
| --- | --- | --- |
| 1. F3 拒答率下降，且准确率不降低 | 拒答 13.6% → 4.5%；准确率 +11.4 | 满足（两者的区间都跨 0） |
| 2. F2 被误导率不升高，且纠正题数 ≥ 5 | 被误导率 −18.2，区间不跨 0；纠正 12 题 | 满足 |
| 3. 无故障 Dev 相对 B3 + 修复不显著下降，区间下界 ≥ −5 | 96.0% 对 96.7%，差 −0.7 [−4.0, +3.3] | 满足 |

**三条全部满足。** 这也是本项目第一次测到多角色架构相对单模型有显著收益：F2 列错位下，B3v2 比 B2 准确率高 20.5 个百分点，被误导率低 20.5 个百分点，区间都不跨 0。F3 下 B3v2 比 B2 高 13.6 个百分点，区间下界恰好是 0。

无故障 Dev 上，B3v2 为 96.0%（94 / 98 / 96），B2 + 修复为 98.7%，差 −2.7 [−6.7, +0.7]，不显著。可见在证据干净时，多角色仍然没有收益。

## 新出现的问题

- **报错**：B3v2 共 5 次报错，按规则都算答错：
  - 4 次是规划结果不合法：3 次子问题超过 6 个的上限（「plan size」），1 次依赖关系无效。
  - 1 次是 JSON 格式修复后仍缺字段。
- **对照**：同样的 B3 + 修复配置，在第 1 轮故障运行和格式修复 Dev 运行中都没有出现规划结构错误。可能的原因是 v2 的交叉核对反馈让规划者不断追加子问题。

直接的修复办法是在规划的 schema 里限制子问题最多 6 个，并在反馈里提示「合并已解决的子问题」。这是下一轮可以做的小改动，需要单独评估。

## 必须说明的限制

- **v2 是在看过这批 Dev 故障结果后设计的**：在同一批题和同一份注入计划上评估，收益很可能偏高。规则是通用的来源优先级和核对规则，没有写入任何具体题目。但在独立数据上验证之前，只能说「在 Dev 故障条件下有效」。
- **只有 1 轮**：故障条件每个配置只跑了 1 轮，F3 的几个差值区间都跨 0 或压在 0 上。
- **F1 几乎测不出差别**：两个版本都很少被 F1 误导。
- **对 B2 的比较是跨轮的**：B2 的故障运行来自第 1 轮，不是与 B3v2 同时跑的。同一份注入计划、同一个接口，但运行时间不同。
