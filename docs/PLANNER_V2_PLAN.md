# 规划者 v2（规划上限修复）：设计与事先登记

2026-09-25，在任何正式运行之前写定。

## 起因

[核验角色 v2](VERIFIER_V2_RESULTS.md) 共 282 次运行中出现 4 次规划结构报错，按规则都算答错。同样条件下，B3 + 修复（v1 核验）从未出现过这类报错。逐条查看轨迹后确认了两个原因：

- **子问题超过上限**（3 次）：核验角色 v2 每要求一次交叉核对，规划者就新增一个「交叉核对 X」子问题，计划涨到 7 项，超过 6 项的上限，程序直接报错退出。
- **依赖前向引用**（1 次）：一个子问题依赖了排在它后面的子问题（S5 依赖 S6）。

## 改动（`planner: "v2"`，v1 保持冻结）

1. **schema 上限**：在规划 schema 的 `plan` 上加 `minItems: 1` 和 `maxItems: 6`。启用格式修复后，超出上限的规划会带着校验错误重试一次，而不是直接报错退出。
2. **提示词**：`PLANNER_V2_NOTE` 要求把交叉核对并入被核对的原子问题，不新增子问题；需要腾出位置时合并已解决的子问题；依赖只能引用排在前面的子问题。
3. **不合法规划转为反馈**：依赖关系无效或引用了未观测证据的规划，不再报错退出。本步动作不执行，规划者收到 `INVALID_PLAN` 反馈，并消耗一次重规划机会。
- **其余不变**：配置 [bench_b3_graph_repair_v2_planner_v2.json](../configs/bench_b3_graph_repair_v2_planner_v2.json) 与 B3v2 只差 `planner: "v2"`。下文称 B3v2p。

## 评估（事先登记）

- **运行**：与 B3v2 相同，故障条件 F1–F3 各 1 轮（同一份注入计划），加上无故障 Dev 3 次，严格串行（`CFG=b3_graph_repair_v2_planner_v2 ./scripts/run_b3_ablation.sh`）。
- **主要判定**：规划结构报错（plan size / invalid plan dependencies / unseen plan evidence 导致的运行中断）在 282 次运行中为 0。B3v2 是 4 次。
- **非劣判定**：无故障 Dev 上，B3v2p 相对 B3v2 的配对差，95% 区间下界不低于 −5 个百分点。
- **描述性报告**：
  - 各故障下的准确率、被误导率、拒答率与 B3v2 的配对差；
  - `invalid_plan` 事件次数与格式修复次数；
  - 成本。
- **以上改动都不涉及核验逻辑**，故障条件下的结果预期与 B3v2 相近。差异在区间以内时，不据此声称有改进。

## 已知偏差

- **修复针对的是已观测到的报错**：同一批 Dev 题上的报错率偏乐观。报错本身出现次数少（B3v2 为 4/282），1 轮评估的检验力有限，0 次报错不能证明报错已被根除。
