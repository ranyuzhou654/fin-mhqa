# 上下文压缩 compact_v1：结果

2026-09-29。按[事先登记的设计](CONTEXT_V1_PLAN.md)进行。对照组是 B3v2p（B3 + 修复 + 核验 v2 + 规划者 v2），实验组 B3v2pc 与它只差 `context_policy: "compact_v1"` 这一项。

## 完成情况

- **运行**：金丝雀 5/5 通过；三类故障各 1 轮（132 次），加无故障 Dev 3 次（150 次），共 282 次。报错 0 次，审计全部通过。
- **次要配置**：B2 + compact_v1 按设计是「额度允许时再跑」，本轮没有跑。

## 判定：未通过（2 项不满足）

| 事先登记的判定 | 标准 | 结果 | |
| --- | --- | --- | --- |
| 效率：无故障 Dev | 每题平均输入 token 减少 ≥ 40% | **−37.2%**（90,452 → 56,798） | ❌ |
| 效率：F1 / F2 / F3 | 同上 | −40.6% / −43.5% / −41.7% | ✅ |
| 不退步：无故障 Dev | 准确率配对差 95% 区间下界 ≥ −5 pp | +1.3 pp [−1.3, +4.0] | ✅ |
| 不退步：F1 | 有效计划上区间下界 ≥ −10 pp | +2.9 [−5.9, +11.8] | ✅ |
| 不退步：F2 | 同上 | −2.3 **[−13.6, +9.1]**（3 题变好、4 题变差） | ❌ |
| 不退步：F3 | 同上 | +4.5 [0.0, +11.4] | ✅ |

- **口径**：设计要求对照组中那 2 次旧的传输报错按两种口径分别计算。另一种口径是剔除这 2 题（在三类故障中都剔除）；剔除后 F2 为 −4.8 [−16.7, +7.1]，结论不变。见 [两种口径](../evidence/context_v1/fault_pairs_excluding_old_transport_errors.json)。
- **结论**：按事先登记的规则，compact_v1 **不采纳为默认配置**。进入 Test 的最终配置仍然是 B3v2p。

## 结果怎么读

**准确率没有下降的迹象**：

| 条件 | B3v2p | B3v2pc（压缩） |
| --- | --- | --- |
| 无故障 Dev（3 次平均） | 98.0% | **99.3%**（98 / 100 / 100），49 题三次都对 |
| F1 准确率 / 被误导率 | 94.1% / 2.9% | 97.1% / 0.0% |
| F2 准确率 / 被误导率 | 81.8% / 11.4% | 79.5% / 15.9% |
| F3 准确率 / 被误导率 | 95.5% / 0.0% | 100% / 0.0% |

F2 没通过判定，原因是只跑了 1 轮、只有 44 题，区间太宽：点估计 −2.3 pp，只相差 1 题（4 题变差、3 题变好）。按规定不能据此说它有害，也不能说它无害。

**token 节省略低于离线测算**：

| 条件 | 每次模型调用的输入 token | 每题模型调用次数 | 每题输入 token |
| --- | --- | --- | --- |
| 无故障 Dev | −42.5% | 5.96 → 6.51（+9%） | −37.2% |
| F1 | −43.2% | 6.93 → 7.25 | −40.6% |
| F2 | −45.1% | 7.39 → 7.59 | −43.5% |
| F3 | −44.5% | 6.84 → 7.18 | −41.7% |

- **单次调用**：压缩使每次调用的输入减少 42–45%，接近离线测算的 50%。离线测算假设轨迹不变，所以会偏高一些。
- **调用次数**：模型的调用次数多了 3–9%，所以按题计算，节省被抵消了一部分。这正是设计中「已知局限」预料的情况：模型看到压缩后的输入，行为会随之改变。
  - 无故障 Dev 上多出来的调用最多，于是跌到 40% 门槛以下。
  - 多出来的调用主要是重复检索还是重规划，还没有逐条分析。
- **输出与耗时**：输出 token 大致持平，无故障 Dev 上 +3%，故障条件下 −4% 到 −13%。三类故障下每题耗时的变化在 ±10% 以内，无故障 Dev 的耗时没有统计。
- **缓存**：缓存命中比例基本不变，都在 47% 左右，说明压缩策略保持了前缀稳定。

**与单模型 B2 对比**：压缩后的四角色仍然明显优于 B2，F2 高 +18.2 pp [0.0, +36.4]，F3 高 +22.7 pp [+11.4, +36.4]。

## 下一步（需要你决定）

1. **维持现状（推荐）**：Test 用 B3v2p。把 compact_v1 作为「可以省约 37–44% 输入 token，准确率未见下降」的描述性结果写进报告，不宣称它已经通过验证。
2. **补一轮 F2 验证**：新登记一轮评估，只重跑 F2（2 轮，约 1.5 小时）来收窄区间。
   - 需要先登记，否则就成了「没过就补跑」。
   - 效率判定在无故障 Dev 上已经没过，补跑 F2 也改不了整体判定。
3. **分析多出来的调用**：离线看无故障 Dev 上多出来的模型调用是做什么的，再决定要不要做 compact_v2。
