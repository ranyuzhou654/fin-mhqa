# benchmark_v1 Dev 基线（S6）

2026-09-24。四个基线配置在冻结的 Dev 50 道题上各跑 3 次，共 12 次运行。模型统一为 `deepseek-v4.1-flash`，都走 OpenCode Go 接口。评分由程序对照冻结答案进行；报错和格式错误都算答错，并留在分母中。**这是 Dev 结果，不是 Test 结论。**

## 主要结果

| 配置 | 3 次准确率 | 均值 ± 标准差 | 平均模型调用 | 平均工具调用 | 平均耗时 | 每次输入 / 输出 token |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| B0 闭卷 | 22 / 18 / 16% | 18.7 ± 3.1% | 1.0 | 0 | 14 秒 | 2 万 / 7.5–12 万 |
| B1 固定 RAG | 62 / 60 / 62% | 61.3 ± 1.2% | 1.0 | 1.8 | 85 秒 | 28 万 / 10 万 |
| B2 单模型 Agent | 90 / 92 / 96% | 92.7 ± 3.1% | 4.2 | 4.5 | 118 秒 | 240–270 万 / 21 万 |
| B3 四角色 Agent | 96 / 96 / 88% | 93.3 ± 4.6% | 5.2 | 4.5 | 124 秒 | 350–370 万 / 44 万 |

**配对比较**（每道题取 3 次运行的平均正确率，对题目做 10,000 次 bootstrap）：

| 比较 | 回答的问题 | 准确率差 | 95% 置信区间 | 变好 / 变差题数 |
| --- | --- | ---: | --- | --- |
| B0 → B1 | 检索的作用 | +42.7 个百分点 | [+28.0, +56.7] | 27 / 4 |
| B1 → B2 | Agent 循环（多步检索、上下文工具、计算器）的作用 | +31.3 个百分点 | [+18.7, +44.7] | 20 / 4 |
| B2 → B3 | 多角色（规划 + 核验）的作用 | +0.7 个百分点 | [−5.3, +6.7] | 7 / 6 |
| B1 → B3 | 完整 Agent 相对固定 RAG | +32.0 个百分点 | [+20.0, +44.7] | 19 / 1 |

结论：
1. **检索和 Agent 循环的收益都显著**，置信区间都不跨 0。
2. **在这个 Dev 集上，多角色架构相对单模型 Agent 没有可测量的收益**：区间跨 0，变好和变差的题数几乎相同。它的代价是模型调用多约 23%，输入 token 多约 40%，输出 token 约为 2 倍。这不能说明多角色永远无用，只说明在当前题目和预算下，它的收益小于测量精度。

## 分题型（3 次均值）

| 题型 | B0 | B1 | B2 | B3 |
| --- | ---: | ---: | ---: | ---: |
| T1 单跳陷阱 | 17% | 100% | 100% | 100% |
| T2 两公司运算 | 13% | 100% | 92% | 100% |
| T3 条件桥接 | 13% | 13% | 92% | 92% |
| T4 比率与增长 | 0% | 63% | 100% | 100% |
| T5 三跳及以上 | 14% | 22% | 83% | 78% |
| T6 无法回答 | 72% | 100% | 94% | 100% |

- 固定 RAG 能解决单跳和简单运算，但几乎解决不了桥接题（13%）和三跳题（22%）。这正是 Agent 循环的收益来源。
- 当前两个 Agent 的主要短板都在 T5 三跳题。
- 误拒率（可回答题却拒答）：B1 为 40%，B2、B3 都是 1.5%。
- 各跳证据引用覆盖：B1 86%，B2 99.3%，B3 99.0%。引用有效性：B1 98.7%，有 1 次引用了未观测到的块，这也是 B1 第 1 次运行中唯一一条审计不通过的原因；B2、B3 都是 100%。

## 报错构成

B2 共 9 道报错：8 道是模型输出的 JSON 不符合 schema，1 道是网络断连。B3 共 8 道报错，全部是 JSON 格式问题：缺少 `reason`、`context` 等必填字段，或多出 `answer_unit_note` 之类的字段。DeepSeek 的 JSON 模式不强制校验 schema。**格式错误大约占 B2、B3 失分的一半**，是下一步最直接的改进点。[明细](../evidence/benchmark_v1_s6/error_breakdown.json)

## 必须说明的限制

- **记忆污染**：B0 闭卷给出了多个精确到小数点后两位的正确答案，例如比亚迪 2025 年上半年营业收入 3,712.81 亿元。模型很可能在训练中见过这些公开财报。因此：
  - 准确率不能单独代表「依据证据作答」的能力，要同时看各跳引用覆盖。B2、B3 都在 99% 以上。
  - B0 的 18.7% 并不是 0 分基线。
- **接口会影响结果**：同一模型 ID，走 Zen 按量接口时，B0 为 10%、B1 为 44.7%；走 Go 接口时分别是 18.7% 和 61.3%。所以 12 次全部统一在 Go 接口上重跑；Zen 上的结果保留在本地 `superseded_zen_*` 目录，不参与比较。
- **Dev 接近饱和**：B2、B3 已达 93%。剩余可提升的空间主要在 T5 和格式错误上。继续比较架构时，差异可能再次落在置信区间以内。
- **数据规模**：只有 50 道题、每个配置 3 次运行，区间较宽。

## 基础设施记录

- 第一轮 B2、B3 是两个进程并行跑的，与只能同时处理 1 个请求的检索服务冲突，产生 924 次 503 错误；B3 第 3 次还遇到 Zen 余额不足（402）。这 6 次运行作废，保留在本地 `invalid_*` 目录。
- 修复：驱动脚本改为串行；检索服务繁忙时在基础设施层等待重试；评分报告列出每次运行的检索错误。本轮 12 次运行的检索错误和繁忙重试都是 0。
- 审计：12 次运行共 600 条轨迹，599 条通过。

证据：[完整报告](../evidence/benchmark_v1_s6/s6_report.json)、[各次审计](../evidence/benchmark_v1_s6)、[运行日志](../evidence/benchmark_v1_s6/s6_driver.log)。复现：`./scripts/run_s6_baselines.sh`，然后运行 `PYTHONPATH=scripts .venv/bin/python scripts/s6_report.py --out <新路径>`。
