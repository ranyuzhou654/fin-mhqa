# 上下文压缩 v2：先诊断，再改进（事先登记）

2026-10-16 写定，任何新的模型调用之前。起因见 [compact_v1 结果](CONTEXT_V1_RESULTS.md)：压缩使每次调用的输入减少 42–45%，但调用次数增加 3–9%，导致无故障 Dev 上按题计算的节省只有 37.2%，没有达到 40% 的门槛。

## 已完成的离线分析（不花额度）

对比无故障 Dev 的各 150 次运行（B3v2p 不压缩 vs 压缩）：

| 每题平均 | 不压缩 | 压缩 |
| --- | --- | --- |
| 核验拒绝次数 | 0.47 | 0.63 |
| 其中「要求交叉核对」，按全部 150 题计 | 51 次 | 84 次 |
| 首次核验就要求交叉核对的轨迹 | 36 / 150 | 62 / 150 |
| 检索次数 | 3.14 | 3.39 |
| 重复检索、重复读取上下文 | 0 | 0 |
| 同一数值被重复要求交叉核对 | 1 次 | 0 次 |

结论：多出来的调用几乎全部来自**首次核验时更频繁地要求交叉核对**，而不是重复检索，也不是违反「不重复拒绝」的规则。

**推测与初步检验**：最初怀疑是第 3 步，即把表格键值块折叠成对应 Markdown 块的引用之后，核验者少看到一个「来源」。但按候选答案的引用结构分组后：
- 引用只来自同一张表的两份副本时，压缩前后的交叉核对比例为 4/10 和 3/5，样本太少，看不出差别；
- 引用跨越多张表时，比例也从 26% 升到 46%。

所以第 3 步不是唯一原因，需要用对照实验来定位。

## 诊断实验：只替换历史视图，重放核验者

- **输入固定**：取 B3v2p 不压缩运行中每条轨迹的**首次核验输入**，共 130 条（其余 20 条轨迹在首次核验之前就已结束），计划、候选答案、此前的拒绝和剩余预算都保持不变。
- **只改核验者看到的历史**，共 5 个版本：

| 版本 | 内容 |
| --- | --- |
| full | 原样输入，重新调用一次，用来衡量核验者自身的随机波动 |
| compact | compact_v1 全部三步 |
| no_drop | 去掉第 1 步：保留全部元数据字段 |
| no_repeat | 去掉第 2 步：重复出现的证据块完整展示 |
| no_twin | 去掉第 3 步：表格键值块完整展示 |

- **核对**（已完成）：
  - full 版本的输入与原始记录逐字节一致；
  - compact 版本与原压缩模块的输出完全相同。
- **规模**：130 × 5 = 650 次核验调用，输入约 1,600 万字符，大约相当于 2 次 Dev 运行的输入量。**等 Test 运行全部完成后再跑。**
- **主要指标**：每个版本「要求交叉核对」的比例，与 full 版本做配对比较，给出 95% bootstrap 区间。

**判定规则**：
- 如果 compact 相对 full 的增加在区间上显著，而去掉某一步之后，与 full 的差异区间跨 0，那么这一步就是主要原因。
- 如果 compact 相对 full 也不显著，说明整轮运行中的差异来自轨迹本身的发散，而不是核验者看到的输入。这种情况下 v2 不改核验视图，转而处理调用次数的问题。

## compact_v2 的改进方向（诊断之后再定稿并另行登记）

根据诊断结果，从下面几项中选择：

1. **来源计数规则**：在核验提示词中明确「独立来源」按来源表格计算，副本与原表算同一来源。不压缩时也存在「把副本当成第二个来源」的问题，所以这一条可能同时影响两种配置。
2. **只对规划者压缩**：核验者每题只调用 1–2 次，却决定了是否要交叉核对，因此可以给核验者保留完整视图，只压缩规划者的输入。节省会少一些，但能避免多出来的调用。
3. **轻度有损**：较早的工具返回只保留已提取的数值和证据编号；当前计划正在引用的证据保留全文。这是原设计中的一项，上次没有实施。

正式评估沿用 v1 的判定标准，但 F2 改为跑 2 轮，避免区间过宽而无法判定。
