# 上下文压缩 v2：先诊断，再改进（事先登记）

2026-10-16 写定，任何新的模型调用之前。起因见 [compact_v1 结果](CONTEXT_V1_RESULTS.md)：压缩使每次调用的输入减少 42–45%，但调用次数增加 3–9%，导致无故障 Dev 上按题计算的节省只有 37.2%，没有达到 40% 的门槛。

## 已完成的离线分析（不花额度）

对比无故障 Dev 的各 150 次运行（B3v2p 不压缩 vs 压缩）：

| 每题平均 | 不压缩 | 压缩 |
| --- | --- | --- |
| 核验拒绝次数 | 0.47 | 0.63 |
| 其中「要求交叉核对」，按全部 150 题计 | 51 次 | 84 次 |
| 首次核验就要求交叉核对的轨迹 | 36 / 150 | 62 / 150 |
| 检索次数 | 3.14 | 3.39 |
| 重复检索、重复读取上下文 | 0 | 0 |
| 同一数值被重复要求交叉核对 | 1 次 | 0 次 |

结论：多出来的调用几乎全部来自**首次核验时更频繁地要求交叉核对**，而不是重复检索，也不是违反「不重复拒绝」的规则。

**推测与初步检验**：最初怀疑是第 3 步，即把表格键值块折叠成对应 Markdown 块的引用之后，核验者少看到一个「来源」。但按候选答案的引用结构分组后：
- 引用只来自同一张表的两份副本时，压缩前后的交叉核对比例为 4/10 和 3/5，样本太少，看不出差别；
- 引用跨越多张表时，比例也从 26% 升到 46%。

所以第 3 步不是唯一原因，需要用对照实验来定位。

## 诊断实验：只替换历史视图，重放核验者

- **输入固定**：取 B3v2p 不压缩运行中每条轨迹的**首次核验输入**，共 130 条（其余 20 条轨迹在首次核验之前就已结束），计划、候选答案、此前的拒绝和剩余预算都保持不变。
- **只改核验者看到的历史**，共 5 个版本：

| 版本 | 内容 |
| --- | --- |
| full | 原样输入，重新调用一次，用来衡量核验者自身的随机波动 |
| compact | compact_v1 全部三步 |
| no_drop | 去掉第 1 步：保留全部元数据字段 |
| no_repeat | 去掉第 2 步：重复出现的证据块完整展示 |
| no_twin | 去掉第 3 步：表格键值块完整展示 |

- **核对**（已完成）：
  - full 版本的输入与原始记录逐字节一致；
  - compact 版本与原压缩模块的输出完全相同。
- **规模**：130 × 5 = 650 次核验调用，输入约 1,600 万字符，大约相当于 2 次 Dev 运行的输入量。**等 Test 运行全部完成后再跑。**
- **主要指标**：每个版本「要求交叉核对」的比例，与 full 版本做配对比较，给出 95% bootstrap 区间。

**判定规则**：
- 如果 compact 相对 full 的增加在区间上显著，而去掉某一步之后，与 full 的差异区间跨 0，那么这一步就是主要原因。
- 如果 compact 相对 full 也不显著，说明整轮运行中的差异来自轨迹本身的发散，而不是核验者看到的输入。这种情况下 v2 不改核验视图，转而处理调用次数的问题。

## compact_v2 的改进方向（诊断之后再定稿并另行登记）

根据诊断结果，从下面几项中选择：

1. **来源计数规则**：在核验提示词中明确「独立来源」按来源表格计算，副本与原表算同一来源。不压缩时也存在「把副本当成第二个来源」的问题，所以这一条可能同时影响两种配置。
2. **只对规划者压缩**：核验者每题只调用 1–2 次，却决定了是否要交叉核对，因此可以给核验者保留完整视图，只压缩规划者的输入。节省会少一些，但能避免多出来的调用。
3. **轻度有损**：较早的工具返回只保留已提取的数值和证据编号；当前计划正在引用的证据保留全文。这是原设计中的一项，上次没有实施。

正式评估沿用 v1 的判定标准，但 F2 改为跑 2 轮，避免区间过宽而无法判定。

## 诊断实验结果（2026-10-16）

**完成情况**：650 次核验调用中 649 次完成，按条目配对比较 129 条。结果见 [verifier_replay.json](../evidence/context_v2/verifier_replay.json)。

| 核验者看到的历史 | 要求交叉核对的比例 | 相对完整历史（95% 区间） |
| --- | --- | --- |
| 完整历史（重新调用） | 33.3% | — |
| compact_v1 全部三步 | 45.7% | **+12.4 pp [+3.1, +21.7]** |
| 去掉第 1 步（保留元数据字段） | 40.3% | +7.0 [−0.8, +14.7] |
| 去掉第 2 步（重复块完整展示） | 45.0% | +11.6 [+3.1, +20.2] |
| 去掉第 3 步（键值块完整展示） | 40.3% | +7.0 [−2.3, +16.3] |

**结论（按事先登记的判定规则）**：
1. **增加来自压缩本身**：输入固定后，压缩仍使交叉核对显著增加，所以整轮运行中多出来的调用，并不只是轨迹发散造成的。
2. **原因是第 1 步和第 3 步**：去掉任一步后，差异的区间都跨 0，增量大约减半，可见两步各贡献一部分。第 2 步（重复块改为引用）与此无关。
3. **核验者自身有随机波动**：同样的完整输入重新调用，交叉核对比例是 33.3%，原始记录是 34/130（26%）。

**尚未回答的问题：更严格是对还是错？** 核验 v2 的第 3 条规则是「关键数值只来自一张表时要求交叉核对」，而同一张表的 Markdown 块和键值块本来就是同一来源。压缩后的视图有可能只是让核验者更准确地执行了自己的规则。
- 按「引用来自几张表」粗分无法判断：多跳题本来就会为不同事实引用多张表，而规则针对的是单个数值。
- 要回答这个问题，需要对 28 条「只有压缩后才要求核对」的条目逐条判断。

**逐条检查的结果（离线，不花额度）**：在这 28 条中，核验者共提出 34 个交叉核对问题。对每个问题，取出它质疑的数值，再查这个数值在核验者看到的历史中出现在几张表里：

| 结果 | 个数 |
| --- | --- |
| 只出现在一张表里：按规则确实应该交叉核对 | 24 |
| 出现在「两张表」里，但都是同一张报表的续表块（例如两段「合并资产负债表」），实际仍是同一来源 | 5 |
| 问题描述里没有数值，无法判断 | 4 |
| 数值不在已观测原文中 | 1 |

**结论**：压缩后多出来的交叉核对，几乎都符合核验者自己的规则。不是压缩让核验者变得多疑，而是完整历史让它把同一张表的 Markdown 块和键值副本当成了两个来源，从而放过了本应交叉核对的情况。
- **对 v1 判定的影响**：compact_v1 未通过判定的原因之一（调用次数增加）实际上来自核验者更准确地执行了规则，而对照组的核验者执行得偏宽松。
- **登记的判定不变**：这不改变已登记判定的结果，compact_v1 仍然算未通过。
- **这也暴露了核验 v2 的一个弱点**：在不压缩的视图下，它会把副本当成独立来源。

**token 占比**：不压缩时，规划者占输入 token 的 75%，核验者占 25%。如果只压缩规划者、核验者保留完整视图，估算每题节省约 31%，低于 40% 的门槛。

## 下一步的选择（需要用户决定）

逐条检查之后，更合理的方向变成：修正的是核验者「数来源」的方式，而不是压缩策略。

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A | 先逐条检查这 28 条，判断更严格是对还是错，再决定方向 | 不花额度，需要人工或模型辅助逐条看 |
| B | 第二轮核验重放：保留与来源、表格身份相关的字段（章节路径、父表 ID、分段、单位来源、是否附带父表），并在提示词中说明「副本与原表是同一来源」。选出与完整历史无显著差异、且 token 最少的方案，再做正式评估 | 重放约 1 小时；正式评估约 4 小时 |
| C | 接受 compact_v1 的现状：准确率不降、核验更严格，只作为描述性结果，不再改进 | 无 |

## 决定（2026-10-16）：到此为止

用户选择方案 C（接受现状，到此为止）：不改动核验者，不再继续压缩方向的实验，把诊断结论作为一项发现写入报告。
- compact_v1 维持「未通过、不采纳」的判定。
- 核验 v2 在不压缩时把副本当成独立来源、偏宽松，这一弱点记入报告的局限部分。如果以后要改进，方向是修正核验者计数来源的方式，而不是压缩策略。
- 已登记 Test 的配置不受影响。
