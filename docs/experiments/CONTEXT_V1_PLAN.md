# 上下文管理 v1：离线测算、设计与事先登记

2026-09-26 写定，在任何真实运行之前。对应路线图 P2。

## 问题

核验 v2 的无故障运行中：

- **每道题平均消耗 9.4 万输入 token**；
- **提示词随步数线性增长**：第 1 步约 1.9K token，第 10 步约 31K；
- **74% 的提示词字符是原样累积的工具返回**。

这是成本高、耗时长的直接原因，也是这周额度被用完的主要原因。

## 离线测算（P2.1，不调用模型）

`scripts/context_budget_analysis.py` 在 4 组共 3,131 个真实模型输入上模拟了各种压缩策略。每个模型输入就是某一步的提示词，4 组分别是 B3 核验 v2 和 B2 + 修复的无故障运行与故障运行。结果见 [offline_estimate.json](../evidence/context_v1/offline_estimate.json)。

**风险指标的定义**：如果模型在某一步的决策里引用了某个证据块（规划中的证据 ID、最终答案的引用、上下文读取的锚点），而这个证据块的全文在该步的输入中被策略隐藏了，就记一次「隐藏引用」。

| 策略 | 做法 | B3 输入 token 减少 | B2 输入 token 减少 | 隐藏引用的输入数 |
| --- | --- | ---: | ---: | ---: |
| S1 精简字段 | 只保留推理需要的字段（ID、公司、类型、页码、表名、单位、正文），去掉哈希、解析路径、质量标记、检索分数等 | 33% | 38–39% | 0 |
| S2 + 去重 | 同一个证据块在同一个输入里只完整出现一次，之后改为引用 | 37% | 43% | 0 |
| S3 + 压缩旧观测 | 旧观测中没有被规划或候选答案引用的证据块，只保留标题行 | 53% | 67–68% | **65–169**（有损） |
| **S4 + 键值块折叠** | 表格键值块（table_kv）如果与同表同分段的 table_md 块同时出现，就改成指向后者的引用 | **50%** | **58%** | **0** |

补充说明：

- **S4 为什么是无损的**：在全部语料中，table_kv 和 table_md 的配对共 2,780 对。逐对核对后，每个键值块里的每个数值都能在它的 Markdown 孪生块里找到；键值块多出的只有「10列（列名未识别）」这类自己生成的列号。另外，正文字符中有 41% 来自同时有孪生块的键值块。
- **S3 为什么不用**：它的节省大部分和 S4 重合，但在 2.5%–9% 的输入中，会隐藏模型当步实际引用的证据。尝试了几个变体（保留最近 2 次观测、固定所有引用过的证据块），最好的也只能减少 48.5%，仍有 47 个输入隐藏了引用。
- **保证前缀稳定**：S4 的所有改写只向前看，已经给出的历史不会因为新观测到来而改变。提示词前缀因此保持稳定，不破坏提供方的缓存；录制的输入中约 51% 的 token 命中了缓存。

## 设计（P2.2，已实现）

- **配置**：新增 `context_policy`，取值 `full`（默认，模型输入保持冻结）或 `compact_v1`。
- **实现**：`src/finmhqa/agent/context_policy.py` 实现 S4，同时作用于规划者和核验者的输入。提示词末尾追加一段说明，解释 `repeat` 和 `same_as` 标记的含义，并说明引用时键值块和 Markdown 块的 ID 都可以用。
- **不变的部分**：图内部仍保存完整历史，轨迹仍记录完整的工具返回，所以审计、评分和发布守卫都不受影响。
- **测试**：
  - 在两个示例的全部 14 个真实模型输入上，每个证据块都能读到，要么是全文，要么通过引用读到全文；
  - 折叠掉的键值块，其数值全部出现在孪生块中；
  - 历史追加任意条后，已有部分保持不变；
  - 结果与离线测算脚本的 S4 完全一致；
  - 图中接入正确，引用被折叠的键值块仍然合法。
- **默认值不改变行为**：录制—重放复查确认，`full` 下 144 道历史题仍逐字节一致。

## 评估（P2.3，事先登记）

- **主要配置**：[B3v2p + compact_v1](../../configs/bench_b3_graph_repair_v2_planner_v2_ctx.json)，与 [B3v2p](../../configs/bench_b3_graph_repair_v2_planner_v2.json) 只差这一项。
- **运行**：`CFG=b3_graph_repair_v2_planner_v2_ctx ./scripts/run_b3_ablation.sh`，内容是金丝雀，加三类故障各 1 轮，加无故障 Dev 3 次，共 282 题次。
- **前置条件**：先完成 P0，即 B3v2p 的无故障 Dev 3 次，作为对照。
- **次要配置（额度允许时再跑）**：[B2 + 修复 + compact_v1](../../configs/bench_b2_flat_repair_ctx.json)，只跑无故障 Dev 3 次。

**判定**（以下都相对 B3v2p，在同一条件下比较）：

1. **效率**：每题平均输入 token 减少 ≥ 40%，无故障 Dev 和三类故障分别计算。
   - 路线图原写的是 ≥ 50%。离线测算表明，无损压缩的上限就在 50% 左右，要求 ≥ 50% 等于逼着采用有损策略。考虑到真实运行中轨迹会变化，在任何运行之前把门槛改为 40%。
2. **不退步**：
   - 无故障 Dev 上，准确率的配对差 95% 区间下界 ≥ −5 个百分点；
   - 每类故障下，有效计划上的准确率配对差区间下界 ≥ −10 个百分点（只跑 1 轮，区间较宽）。
3. **描述性报告**：被误导率、拒答率、模型调用次数、耗时、缓存命中比例、错误分类。

## 已知局限

- **离线测算的前提**：离线测算假设轨迹不变。真实运行中，模型看到的是压缩后的输入，行为可能改变，比如因为看不到原始字段而多检索一次。这正是需要真实评估的原因。
- **与旧运行比较的口径**：B3v2p 的故障运行出自 harness 启用之前，其中 2 次传输报错按旧规则算错；新运行会补跑这类报错。按 [harness 规定](../system/HARNESS.md)，比较时同时给出两种口径。
