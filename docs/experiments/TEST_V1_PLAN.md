## 阶段 A：无故障 Test（本次运行）

- **运行**：每个配置在 Test 的 100 道题上跑 **3 次**，严格串行。顺序为 B2 第 1 次、B3v2p 第 1 次，然后两个配置交替跑第 2、3 次，减少时间漂移对比较的影响。
  - **变更记录（2026-10-16）**：本计划最初写的是每个配置跑 1 次，与 [评测集设计](../benchmark/BENCHMARK_DESIGN.md) §5「最终候选配置在 Test 上跑 3 次」不一致。用户确认按原设计跑 3 次。变更时 B2 的第 1 次运行刚结束、B3v2p 的第 1 次正在进行；没有对任何 Test 运行打分，也没有查看答案正确与否。
  - 每个配置开跑前都要先通过金丝雀，金丝雀用的是 5 道 Dev 题。
  - 额度中断后用 `--resume` 续跑同一次运行，不会另开一次运行。
  - 每次尝试都会追加到 `test_runs.jsonl`。
- **主要判定（H1，非劣）**：B3v2p 相对 B2 的准确率配对差，95% bootstrap 区间下界不低于 −5 个百分点。每道题取 3 次运行的平均正确率，再做配对 bootstrap，与 Dev 的方法相同。
  - 这是对 Dev 结论「无故障时四角色与单模型打平」（−0.7 [−4.0, +2.0]）的确认。
- **描述性报告**：
  - 两个配置各自的准确率与 95% 区间；
  - 分题型、分标签的准确率；
  - 拒答召回率与误拒率；
  - 引用有效性与各跳证据覆盖；
  - 报错分类与成本（模型调用次数、token、耗时）；
  - 相对 Dev 的落差，作为泛化的参考。
- **计分规则**：与 Dev 完全相同。报错和没跑完的题都算错，并保留在分母中。

## 阶段 B：Test 故障注入（另行确认后再跑）

阶段 A 完成后，要等用户确认、并且额度允许，才运行阶段 B。设计在这里先写定，避免看到阶段 A 的结果之后再改。

- **注入计划**：用与 Dev 相同的生成规则和随机种子，为 Test 中可回答的题生成 F2（本期、上期列错位）和 F3（冲突的汇总表，×1.07）两类注入计划。
  - 生成过程只依赖 Test 的标准答案和事实台账，不看任何运行结果。
  - 注入计划里含有据标准答案预先算出的「被误导答案」，所以与 Test 标准答案一样，不纳入 git，只记录 SHA256。
  - F1（单位标错）在 Dev 上两个配置都不受影响，所以不跑。
- **运行**：每个配置、每类故障各 1 轮。
- **主要判定（确认 Dev 上的核心发现）**：
  - **H2**：F2 下，在有效计划上，B3v2p − B2 的准确率配对差 95% 区间下界 > 0；
  - **H3**：F3 下，同样的判定。
- **描述性报告**：被误导率、拒答率、核验角色的纠正与损害次数。

## 已知局限

- **样本量**：每个配置 3 次、100 道题。若两个配置的真实差异只有几个百分点，这次运行分不出来，H1 只能用来排除较大的退步。
- **模型漂移**：Dev 结果是 9 月底跑的，Test 在 10 月中旬跑，模型提供方可能更新了模型。金丝雀只能发现较大的漂移；同一时段内两个配置之间的比较不受这种漂移影响。
- **故障是人为构造的**：阶段 B 的故障不代表真实解析错误的分布。
