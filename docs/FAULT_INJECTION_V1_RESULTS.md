# 故障注入对比 v1：结果（第 1 轮）

2026-09-25。按[事先登记的设计](FAULT_INJECTION_V1_PLAN.md)进行，比较对象是 B2 + 修复（单模型）和 B3 + 修复（四角色）。

- **题目与故障**：Dev 中 44 道可回答题，分别注入 F1 单位标错、F2 列错位、F3 冲突数值三类故障，不加任何提示。
- **规模**：每个配置、每类故障跑 1 轮，共 264 题次，串行执行。
- **审计**：264 条轨迹全部通过，包括每次检索和上下文读取的「原始返回 → 变换」逐字重放。
- **性质**：这是 Dev 上的诊断实验，不是 Test 结论。

## 主要结果

准确率与被误导率都在「有效」计划上计算，即被误导答案与真值不同的计划：F1 34 个，F2、F3 各 44 个。

| 故障 | 配置 | 准确率 | 被误导率 | 拒答率（44 题） | 报错 | 干净参照 → 故障（配对） |
| --- | --- | ---: | ---: | ---: | ---: | --- |
| F1 单位标错 | B2 | 94.1% | 2.9% | 0% | 1 | −4.9 个百分点 [−14.7, +2.0] |
| | B3 | 94.1% | 2.9% | 2.3% | 0 | −3.9 个百分点 [−11.8, +2.0] |
| F2 列错位 | B2 | 61.4% | 29.5% | 2.3% | 3 | **−37.1 个百分点 [−51.5, −23.5]** |
| | B3 | 70.5% | 27.3% | 2.3% | 0 | **−25.8 个百分点 [−39.4, −12.9]** |
| F3 冲突数值 | B2 | 77.3% | 13.6% | 6.8% | 1 | **−21.2 个百分点 [−34.1, −9.8]** |
| | B3 | 79.5% | 6.8% | 13.6% | 0 | **−16.7 个百分点 [−30.3, −4.5]** |

干净参照是同一批 44 题在格式修复 Dev 运行（各 3 次）中的准确率：B2 为 98.5%，B3 为 96.2%。

| 故障 | 准确率差 | 被误导率差 | 拒答率差 |
| --- | --- | --- | --- |
| F1 | 0.0 [−8.8, +8.8] | 0.0 [0.0, 0.0] | +2.3 [0.0, +6.8] |
| F2 | +9.1 [−4.5, +22.7] | −2.3 [−13.6, +9.1] | 0.0 |
| F3 | +2.3 [−9.1, +13.6] | −6.8 [−15.9, 0.0] | +6.8 [−4.5, +18.2] |

## 结论

1. **盲注入的证据错误确实会让 Agent 答错**：
   - F2 列错位和 F3 冲突数值让两个配置的准确率都显著下降，区间都不跨 0。
   - 最难的是 F2：本期与上期数值对调后，数字本身、表格结构和期间标签看起来都合理，约 28–30% 的题直接照错值作答。
   - F1 单位标错几乎无效：两个配置都会用报告级单位声明和数量级核对单位，被误导率只有 2.9%。
2. **按事先登记的判定标准，四角色（核验角色）没有净收益**：
   - 三类故障上，B3 的被误导率都没有显著低于 B2。F3 的区间上界恰好是 0，处在边界上。
   - 核验角色误拦正确候选 36 次，拦下错误候选只有 7 次。
3. **核验角色的作用随故障类型变化，正负相抵**（见[逐题转移](evidence/fault_injection_v1/verifier_effect.json)，比较的是规划者第一次给出的候选答案和最终发布的答案）：

   | 故障 | 纠正：候选被误导 → 发布正确 | 损害：候选正确 → 发布拒答 | 漏过：被误导候选照样发布 |
   | --- | ---: | ---: | ---: |
   | F1 | 1 | 1 | 1 |
   | F2 | **5** | 0 | 12 |
   | F3 | 0 | **6** | 3 |
   | 合计 | 6 | 7 | 16 |

   - **F2**：这是核验角色第一次被测到有价值。它拦下 5 个被误导的候选，规划者重新检索后全部改正，而且没有造成损害。
   - **F3**：它发现摘要表与报表矛盾后反复拒绝，4 道题被拒 3 次。结果 6 个本来正确的候选最终都成了拒答：4 个是重规划预算耗尽，2 个是规划者在被拒后主动放弃。
   - **F3 中 B3 被误导率较低，并不是核验角色的功劳**：B3 规划者第一次给出的候选里只有 3 个被误导，而 B2 没有核验角色，发布了 6 个被误导的答案。差别出在规划阶段。
4. **成本**：
   - B3 平均模型调用 6.2–7.9 次，B2 为 4.6–4.9 次。
   - 输入 token 是 B2 的 1.6–2.2 倍。
   - F3 下 B3 平均每题 319 秒，B2 为 203 秒。

## 必须说明的限制

- **报错只出现在 B2**：共 5 题，都是 OpenCode 接口断连，重试 2 次后仍然失败。按规则算答错，不补跑。排除任一方报错的题后再做配对，有效计划上的正确题数如下，两者基本持平：

  | 故障 | B2 | B3 |
  | --- | --- | --- |
  | F1 | 32/33 | 31/33 |
  | F2 | 27/41 | 28/41 |
  | F3 | 34/43 | 35/43 |

- **只有 1 轮、44 题**：区间较宽。F3 被误导率的区间上界恰好是 0，按设计属于显著性边界，应再各补 1 轮。是否补跑待定。
- **故障是人为构造的**：真实解析错误的分布未知。本结果只说明在这三类错误下各机制的表现。
- **两个配置的规划提示词不同**：B3 的规划者和 B2 的单模型提示词并不相同。所以 F3 被误导率的差异不能全部归到「多角色结构」上。

## 下一步可以改进的点

- **核验角色的拒绝策略**：F3 中出现冲突时，它反复拒绝同一个候选，而不是要求去查主表来裁决。可以把「已发现冲突，候选答案取自主表」列为可以接受的结论，或者在第 2 次拒绝后改为交给规划者裁决。这一改动可以在同样的故障条件下做消融测试。
- **F2 的漏检**：17 个被误导候选中，核验角色只拦下 5 个。可以要求它核对期间标签和同一指标在其他表中的值，这是 F2 最直接的检查方式。
